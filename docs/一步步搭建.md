# SupportFlow：一步步搭建与理解

代码已经写在当前目录。你不用同时读完全部文件，每一步先运行，再看对应函数，再做一个小修改。
所有运行命令从项目根目录执行，先 `conda activate langchain`。

## 第 0 步：确认运行的解释器

```powershell

```

## 第 2 步：从 PDF 建立向量知识库

先运行下面两条命令，再阅读 `supportflow/ingest.py`、`embeddings.py`、`retrieval.py`：

```powershell
python -m scripts.ingest
python -m scripts.lesson2
```

项目提供三页模拟政策 PDF。lesson2 会打印页面、切分结果、向量维度和检索出处。

建库阶段是：**Loader → Splitter → Embedding → Chroma**。

1. `load_pdf_documents()` 使用 `PyPDFLoader` 读取每一页。
   返回 `Document`，`page_content` 是字符串，`metadata` 保存文件名、页码和政策编号。
   它做文本提取，不会给扫描图片做 OCR。
2. `split_documents()` 使用 `RecursiveCharacterTextSplitter` 将长文本分成块。
   先尝试按换行、句号等边界切分，必要时按字符切分；每块保留页面元数据。
   `CHUNK_SIZE=240` 是目标最大字符数，`CHUNK_OVERLAP=40` 允许相邻块重叠，
   保留句子跨块时的上下文。重叠不保证每个边界恰好40字，短页也不必切成多个块。
3. `build_index()` 调用 `Chroma.add_documents()`；内部先调用 `embed_documents()`
   给文本块编码，再将文本、向量、metadata 一起持久化。
4. 索引放在 `runtime/knowledge` 中。清单记录 PDF 内容指纹、切分参数和向量模型。
   不变时复用；变化时新建快照，全部写入成功后才切换，失败保留之前的快照。

提问阶段是：**问题 → embed_query → Chroma 检索 → 文本证据 → 模型回答**。

`Retriever.__init__()` 打开已存在的向量库；`search()` 把问题编码，执行余弦距离搜索，
返回文本块、文件名、页码和相似度。这里不是把向量交给聊天模型，
而是把向量找到的**原始文本**放入 `ToolMessage`，供模型阅读。

当前不需要密钥，是因为 `DemoEmbeddings` 用固定哈希将中文二元词编码为1024维向量。
它不是训练过的语义模型，不保证“坏了”和“故障”这样的近义表达会靠近。
真实模式通过 `EMBEDDING_PROVIDER=api` 接入独立的兼容 `/embeddings` 服务，
参数在 `.env.example`。建库和提问必须用同一个向量模型；换模型后重新 ingest。
聊天模型与嵌入模型职责不同，密钥和服务商也可以不同。

**你需要能解释：** Chroma 存了什么？为什么建库用 embed_documents，提问用 embed_query？
为什么不用每次重新给政策编码？找到相似文本是否保证有答案？

**修改练习：** 将 `.env` 中 `CHUNK_SIZE` 设为80、`CHUNK_OVERLAP` 设为16，
重新运行 ingest 和 lesson2，观察文本块数与检索返回正文的变化，然后还原并再次建库。
修改后服务需重启。`data/policies.json` 的 rules 继续负责业务判断；
修改示例政策时同时维护正文与规则，再用 `scripts.create_policy_pdf` 更新示例 PDF。

## 第 3 步：将业务函数变成工具

阅读 `supportflow/tools.py` 的 `build_tools()`。

`@tool` 根据函数名、docstring、参数类型生成工具说明与 JSON schema。
模型选择工具时生成这样的结构：

```json
{
  "name": "get_order",
  "args": {"order_id": "O1001"},
  "id": "某次调用的唯一编号",
  "type": "tool_call"
}
```

模型没有直接运行函数；真正执行的是工具节点，结果放入与调用 id 配对的 `ToolMessage`。
schema 中没有 user_id，因为它从服务器会话注入。

`request_exchange` 只准备申请，不直接创建工单。这种拆分让写入必须经过图里的审批逻辑。

**你需要能解释：** 提示词写“不要越权”与数据库按用户查询，哪一个是实际权限边界？

**修改练习：** 阅读每个工具的描述，想一想描述不明确时模型会如何选错工具。
先只改 docstring，再配置真实模型评测工具选择；规则模式不会因为 docstring 改动而改变决策。

## 第 4 步：理解 Agent 循环

先阅读 `supportflow/demo_model.py`，再阅读 `supportflow/graph.py`。

`AgentState` 保存：

| 字段 | 含义 |
| --- | --- |
| messages | HumanMessage、AIMessage、ToolMessage 的历史 |
| session_id | 会话编号，用作 checkpoint thread_id |
| user_id | 后端认定的用户身份 |
| turn_id / turn_start | 识别当前轮与当前轮起始位置 |
| steps | 当前轮已调用模型/规则决策的次数 |
| events | 已完成节点的工具、耗时、结果和 usage |

`add_messages` 是消息 reducer，负责合并消息。`events` 用追加 reducer；其他字段直接更新。

执行路径：

```text
agent：生成回答或 tool_calls
  ├─ 没有 tool_calls → END
  └─ 有 tool_calls → tools：执行，生成 ToolMessage → agent
```

这是 Agent 的核心：模型观察工具结果，然后决定继续调用工具还是完成任务。
规则模式只是用预设规则模拟这一协议，真实模式用 `ChatOpenAI.bind_tools().invoke()`。

运行：

```powershell
python -m scripts.demo
```

预期：先追问订单号，再执行 get_order → search_policy → check_exchange → 等待确认。
确认后出现 request_exchange 的执行结果和工单号。该脚本使用独立数据库。

**你需要能解释：** 为什么需要最大步数？工具报错怎样被模型观察？

## 第 5 步：理解暂停、恢复和幂等

阅读 `graph.py` 的 `tools_node()` 和 `service.py` 的 `approve()`。

当申请符合条件：

1. 生成与会话、工具调用绑定的 approval_id。
2. `interrupt()` 保存状态并暂停，向调用方提供确认内容。
3. 用户通过专用审批接口提交真实布尔值。
4. 后端检查会话归属、确认编号、已保存的决定。
5. `Command(resume=...)` 恢复图。
6. 重新校验申请，再调用 `create_ticket()`。

**重要：恢复时整个 tools 节点会重新执行。** 所以 interrupt 前只有读取和校验，
没有先写数据库；真正写入也有 request_id 和 order_id 唯一约束。

确认后模型总结失败时，工单可能已经存在，不能盲目把整个任务当成未执行。
`/retry` 或重复同一审批决定会从 checkpoint 继续，不产生第二张工单。

`interrupt()` 抛出的是框架暂停信号，因此它必须在通用异常捕获范围之外。
否则可能被误当成工具失败，图就无法等待用户确认。

**你需要能解释：** checkpoint 保证状态保存，是否就等于业务操作 exactly-once？
不是；外部写入还需要幂等键和数据库约束。
